# 酒馆生图 · CLIProxyAPI

一个无需构建、无需酒馆助手的 SillyTavern 扩展。右侧悬浮按钮打开控制面板，把所选楼层之前的最近聊天与预设拼接，调用 CLIProxyAPI 生图，再保存到酒馆并作为图片附件插入该楼层。保留原文和原有图片。支持使用酒馆自带后台转发，无需浏览器直接访问生图服务。

**从 1.0 升级：**原有配置会保留“浏览器直连”，避免未经选择就把 `127.0.0.1` 的含义改到另一台机器。远程部署酒馆的用户，请按下方说明启用代理，并在面板中切换为“酒馆后台转发”。新安装默认使用后台转发。

## 安装

### 推荐：在酒馆中通过仓库安装

1. 打开酒馆顶部的“扩展”面板，选择“安装扩展”。
2. 粘贴以下仓库地址并安装：

   ```text
   https://github.com/luoyukami/tavern-image-bridge
   ```

3. 刷新页面，在扩展管理中确认“酒馆生图 · CLIProxyAPI”已启用。
4. 后续在酒馆的扩展管理中检查更新并更新此扩展，然后刷新页面。扩展同时启用了酒馆支持的 `auto_update` 标记；具体自动更新时机由酒馆版本决定。

### 手动安装

1. 解压安装包，找到 `tavern-image-bridge` 文件夹。
2. 将**整个文件夹**放到 SillyTavern 安装目录中的以下任一位置：
   - 当前用户：`data/<你的用户目录>/extensions/tavern-image-bridge/`，默认通常为 `data/default-user/extensions/tavern-image-bridge/`。
   - 所有用户：`public/scripts/extensions/third-party/tavern-image-bridge/`。
3. 确认 `manifest.json` 直接位于上述文件夹内，不要多套一层文件夹。
4. 刷新酒馆页面，在扩展管理中确认“酒馆生图 · CLIProxyAPI”已启用。右侧出现图片按钮；扩展设置中也有“打开酒馆生图”入口。

酒馆的“安装扩展”输入框需要 Git 仓库 URL，不能直接填 ZIP 路径。手动安装的文件副本不会变成 Git 仓库；需要便捷更新时，建议使用上面的仓库安装方式。GitHub 自动生成的源码 ZIP 文件夹可能带有分支名或版本号，手动安装时请将文件夹重命名为 `tavern-image-bridge`。

安装无需 `npm install`，也无需修改酒馆服务端代码或安装额外服务器插件。后台转发模式需要修改酒馆的配置并重启，见下文。建议使用当前稳定版酒馆；代码包含旧版 `extra.image` 与新版 `extra.media` 两种附件处理方式，最低版本声明为 1.12.0，但未逐一实测所有历史版本。

## 远程酒馆：让请求从酒馆服务器发出

### 配置一次即可

1. 在酒馆服务器上，编辑**实际使用的** `config.yaml`，通常位于酒馆根目录。Docker 部署时编辑映射到容器内的配置文件，不要修改 `default/config.yaml`。
2. 找到并修改这一项，避免重复添加同名配置：

   ```yaml
   enableCorsProxy: true
   ```

3. 重启酒馆进程或容器。
4. 更新扩展并刷新页面，将面板的“连接方式”设为 **酒馆后台转发（推荐）**。
5. API 地址填写**从酒馆服务器能访问的** CLIProxyAPI 地址，填好客户端 API Key，然后点击“读取模型”检查连接。

请求路径是：`当前设备的浏览器 → 同源酒馆 /proxy/ → CLIProxyAPI`。模型列表、生图请求和返回图片 URL 的下载都会走后台。浏览器只连接酒馆，不需要 CLIProxyAPI 配置浏览器 CORS，HTTPS 酒馆也不会因为上游使用 HTTP 而触发浏览器混合内容拦截。不要把酒馆网页地址当成 CLIProxyAPI 地址填写。

### 地址怎样填

| 部署方式 | API 地址示例与含义 |
| --- | --- |
| 酒馆与 CLIProxyAPI 在同一台服务器，均直接运行 | `http://127.0.0.1:8317/v1`；这里的 `127.0.0.1` 就是服务器 |
| 酒馆与 CLIProxyAPI 分别位于同一 Docker 网络的两个容器 | 例如 `http://cliproxyapi:8317/v1`，使用实际的 Docker 服务名；API 需监听容器可达的接口 |
| 酒馆在 Docker 内，CLIProxyAPI 在宿主机 | 使用容器能访问到的宿主机地址或网关；`127.0.0.1` 只指酒馆容器 |
| CLIProxyAPI 在另一台机器 | 使用酒馆服务器能够访问到的内网地址或域名 |

酒馆内置代理受酒馆自身访问控制和服务器出站网络设置影响。开启时请保留已有登录、IP/Host 白名单等保护；如启用了 `privateAddressWhitelist`，只把需要访问的 CLIProxyAPI 内网地址加入允许列表，不要为此关闭所有保护。配置与转发实现见 [酒馆配置文档](https://docs.sillytavern.app/administration/config-yaml/) 和 [原生代理源码](https://github.com/SillyTavern/SillyTavern/blob/release/src/middleware/corsProxy.js)。

**HTTP Basic Auth 限制：**酒馆原生 `/proxy/` 会转发 `Authorization` 给上游。若酒馆或其前置反代同时要求 HTTP Basic Auth，该请求头会与 CLIProxyAPI 的 Bearer Key 冲突。扩展会在收到 Basic 认证挑战时说明原因；这种部署需改用保留访问保护的同源定向反代、专门的服务端插件，或选择浏览器直连。本版不会关闭认证，也不会在后台模式失败后自动改走浏览器。

### 浏览器直连模式

当 API 本来就在当前设备上，或已提供可跨域访问的 HTTPS 地址时，可以主动选择“浏览器直连”。此时 `127.0.0.1` 指浏览器所在设备，需要 API 允许 CORS，并满足浏览器的 HTTPS/HTTP 限制。这是 1.0 版本的连接方式。

## 首次使用

1. 打开一个有聊天内容的会话，点击右侧悬浮按钮。
2. 选择 **连接方式**，然后填写 **API 地址**，例如 `http://127.0.0.1:8317/v1`。后台转发模式按酒馆服务器的网络环境填写；直连模式按当前设备填写。也可填服务根地址或完整的 `/v1/images/generations` 地址。自定义反代前缀请保留，例如 `https://example.com/proxy/v1`。
3. 填入 CLIProxyAPI 的**客户端 API Key**，不要填管理面板的管理密钥。
4. 图片模型默认是 `gpt-image-2.5`。可点击“读取模型”，再输入或选择代理支持的名称；也支持 `gpt-image-2.5-flare`、`gpt-image-2.5-sunburst`、`gpt-image-2` 或带提供商前缀的实际模型名。读取模型只调用 `/v1/models`，不会生图。读取成功后模型列表会自动展开，点一项即可选用；也可以点“选择模型”随时开关列表，或直接在输入框里改写。列表是界面自己画的，不依赖浏览器的 `datalist`（iOS Safari 不支持 `datalist`，所以手机上不会弹出原生候选）。
5. 设置“最近聊天层数”，编辑生图预设，然后点击“生成并插入楼层”。
6. 需要连续出图时勾选 **模型回复结束后自动生图**，之后每次模型回复结束都会自动为刚生成的那一层生图并插入。
7. 想让同一个角色后面的图长得像：在「参考图」里上传一张满意的图，或点「从楼层选图」把已经生成过的插画挑进来（见「参考图」一节）。

默认读取最近 6 层有效聊天，图片插入最新有效楼层。下拉框也可选择最近 100 层中的某一层，此时聊天截取范围截至该层。界面中的“第 1 层”对应酒馆内部消息索引 0。

## 预设与上下文

预设只有一份，可直接修改，自动保存。支持四个占位符：

| 占位符 | 替换内容 |
| --- | --- |
| `{{chat}}` | 截至目标楼层的最近 N 层有效聊天，包含楼层号和说话人 |
| `{{char}}` | 酒馆里这张角色卡的名字（= `name2`）。注意它常常只是**卡片标题**（例如卡叫「租借女友」，剧情里的角色其实叫「伊蕾娜」），预设里别拿它当人物称呼用，角色是谁以聊天内容为准 |
| `{{user}}` | 当前用户名 |
| `{{appearance}}` | 角色形象档案（见下一节）；档案为空或关闭注入时替换为空 |
| `{{reference}}` | 参考图说明块（见「参考图」一节）；没有选中的参考图时替换为空 |

不包含 `{{chat}}` 时，聊天内容会自动追加到预设末尾；不包含 `{{appearance}}` 时，形象档案（若已开启且非空）追加在最后，`{{reference}}` 同理追加在档案之后。展开“预览发送内容”可检查完整请求文本，参考图清单另在下方列出。默认预设要求直接生成当前场景插画，不调用另一个文本模型来改写提示词。

“有效聊天”指非系统/非隐藏、且有文本的消息。会移除 HTML 标签、`think/thinking` 块、脚本样式块和图片 Markdown；不读取 `extra` 中的思维链、角色卡、世界书或历史图片到文本里（「从楼层选图」只列出图片路径供你挑，图片本身不进文本提示词）。需要保持人物细节时，可把人物外貌写进预设，或用参考图。单次提示词超过 32000 字符时会提示减少层数，不会静默截断。

## 角色形象记忆

面板第二个标签页。用一个文字模型把角色的**固定外形**记成档案（明显的身体特征 + 常穿的衣物配饰），生图时作为**保底**一起发送；最近几层没写穿着、画面也不会跑偏。临时的伤势、污渍、表情、情绪、姿势与随身物品都不收进档案——这些变化太快，只会干扰作画。

- **存放位置**：按聊天保存，写进该聊天的 `chat_metadata`（跟着聊天文件走，换设备也在）。旧版酒馆没有元数据接口时，退回到扩展设置里按聊天分区保存。
- **总结模型**：与生图分开的连接，同样按 OpenAI 格式（`/v1/models`、`/chat/completions`）。API 地址和 Key 留空即沿用生图那一份；文字模型名可以点「读取模型」从该连接拉取列表，再点「选择模型」点选，也可以直接手写。请求与生图异步，互不等待。
- **名字以正文为准**：酒馆给楼层打标签用的是角色卡的名字，那可能只是卡片标题。提示词会明确交代这一点（「酒馆里这张角色卡的名字：…，可能只是卡片标题」＋「消息标签里出现的名字：…（以正文为准）」），系统提示词也要求只写正文里真实使用过的称呼；标签名在正文里从没被当作称呼用过就不建档案。档案里已有的同名条目会在条目下提示，确认后可以删掉。
- **总结请求**（「总结当前形象」）：把最近 N 层聊天一次性交给模型，产出完整档案。N 可设为 1–200，默认 40。只收两类内容：明显的身体特征（发色发型、瞳色、肤色、体型、旧疤/胎记/纹身/义肢/兽耳等长期特征）与穿戴物（上衣、下装、外套、鞋、帽子、手套、围巾、常戴配饰）。返回的条目按角色名合并进现有档案，没被提到的角色保留原样。
- **对比请求**（「对比最新回复」）：只发送**最新一层模型回复**和现有档案，让模型判断固定外形是否变化。换衣、脱衣、换鞋、摘戴配饰、剪发染发、新增永久疤痕这类才算变化；淋湿、沾血、脏污、出汗、脸红、新伤口包扎、妆容、表情、情绪、姿势与随身道具都不算。有变化时返回变化角色的**完整**新描述（整条替换），没变化时只返回 `NoUpdate`，前端判定后不做任何改动。这条请求很短，是所有自动维护的基础。
- **自动维护**：勾选“模型回复结束后自动对比更新”后，每次模型回复结束都会发一次对比请求。手动停止生成、最新楼层是用户消息、同一层已经对比过、或已有形象请求在进行时都会跳过。
- **查看实际发送的提示词**：形象记忆页有「查看会发给形象模型的提示词（总结 / 对比）」，展开就能看到两个请求的 system 与 user 原文（`{{user}}` 已展开成真名）；上一条 details 是发给生图模型的那份形象文本。
- **注入生图**：勾选“生图时把档案作为保底发送”后，档案会以「角色形象档案 · 上一次的存档，可能不是最新」为标题附加在提示词末尾，并明确要求以聊天内容为准；也可在预设里用 `{{appearance}}` 自行安排位置。
- **用户形象不入档**：用户（`{{user}}`）以及所有 `is_user` 消息的说话人都会被排除，模型万一返回也会被丢弃。
- **校验**：返回内容去掉代码块后按第一段配平 JSON 解析（也接受 `[{name, appearance}]` 形式），角色名会对齐到聊天里的写法，描述去掉 HTML/图片后压成单行；提示词要求每条不超过 80 字，代码兜底截到 800 字符、最多保留 12 个角色；解析失败只报错、绝不动现有档案。
- 提示词口径改紧后，旧档案里那些「袖口有酒渍、手边放着铜灯」之类的细节不会自动消失：点一次「总结当前形象」就会按新口径把每个角色整条重写。
- **换 swipe / 重新生成 / 分支**：换 swipe、重新生成或手改楼层后，都会拿新的那层内容重新对比一次（同一楼层同一文本不会重复请求，不会白花额度）。酒馆的「创建分支 / 检查点」只把 `main_chat` 写进新对话的元数据，档案不会跟过去，所以扩展在本机额外保留最近 8 个对话的档案副本：在分支里打开面板会提示一键「沿用母对话的档案」。分支点早于档案记录的时间时，建议改用「总结当前形象」按分支内容重建。删除楼层不会立刻改档案，下一次对比或总结会按可见内容纠回来。
- 面板里可查看每个角色的描述、单个删除、二次确认后清空，以及“查看会发给生图模型的形象文本”。切换聊天时档案随聊天切换。

## 参考图（角色一致性）

面板「生图」页的**参考图**一栏。选中一张图后，本次生成会把图作为**参考**一起发给模型，用来固定角色的长相——**脸、身材、画风**看参考图，姿势、动作、服装、道具、场景、天气、光线一律以聊天原文为准。这是「同一角色出一张之后，后面的图能长得像」的开关：生成一张满意的插画，从楼层里把它挑成参考图，之后就能一直沿用。

两种来源：

- **上传图片**：从本机选一张图（可多选）。上传前会在浏览器里缩放：长边超过 1280 就等比缩到 1280，超过约 1.5 MB 会重编码为 JPEG（有透明通道时铺白底）。压完通过酒馆原生 `/api/images/upload` 存进你的图片目录（文件名 `tavern-reference-…`），设置里只记路径。
- **从楼层选图**：列出当前聊天里所有含图的楼层（生成过的插画、酒馆图库、正文里的 Markdown/`<img>` 图片），最新的排在最前，点一下即加入。图片只记路径 + 楼层号。

行为与限制：

- **上限 2 张**：每张参考图都会变成一次输入图片 token（实测一张约 1000–1300 tokens，两张实测 2545），上传也要多走一份流量，所以上限刻意压到 2（够「一张脸 + 一张全身」）。到上限时再点会提示先移除一张。
- **选中就一直带着**：参考图按聊天保存（`chat_metadata`），换设备、重开聊天都还在，直到你点「清空参考图」（两次点击确认）或单张移除。每张旁边可以单独停用、可以写一行备注（例如「只参考画风」），备注会原样写进提示词。
- **有参考图才走 `/v1/images/edits`**，没有参考图时请求与以前完全一致（`/v1/images/generations`），老路径零改动。
- **生成前预检**：点生成时先把选中的图取成 base64。某一层被删、或切了分支导致某张失效时，会明确报出是**哪一张**取不到，并给出「忽略取不到的参考图继续」（用剩下的继续画）或先移除后重来；不会静默丢图，也不会白花一次生图。
- **说明可改**：`参考图说明` 默认为
  「【参考图】本次附上 N 张参考图，只用来固定角色的长相、身材与画风：… 除此之外的一切——姿势、动作、服装、道具、场景、天气、光线、构图——一律以【聊天情节】里的最新剧情为准，参考图里的姿势、背景和服装不要照搬。若参考图与【角色形象档案】冲突：脸和身材以参考图为准，服装与场景以聊天原文为准。」
  可在 `{{reference}}` 占位处自选位置（不写占位就追加到末尾，与 `{{appearance}}` 同规则），文案本身可直接改。
- **和形象档案的关系**：档案是文字保底（写清发色发型、瞳色、体型、常穿衣物），参考图是视觉基准。两者都开时，脸和身材以参考图为准，服装与场景以聊天原文为准。
- **分支与检查点**：酒馆的分支只带 `main_chat`，参考图不会跟过去。扩展在本机保留最近 8 个对话的参考图副本，在分支里打开面板会出现「沿用母对话的参考图」。
- **实测**（2026-09-29，`gpt-image-2.5` 走 CLIProxyAPI）：一张参考图约 21 秒，两张约 31 秒；参考图里的发色、肤色、脸颊印记、上衣与整体画风都保留，而姿势、道具、环境完全按聊天原文重新构图。参考图不是"贴图合成"，是模型据此重画。
- **已知**：这条 Codex 渠道会忽略请求里的 `size` / `quality`（要 1024×1024 实际回 1254×1254，要 1536×1024 回 1370×1148，`quality` 一律报 `low`）；参考图不改变这一点。

## 图片与悬浮控件

- 图片与悬浮设置中可选择方形、横向、纵向、自动尺寸以及质量。`xhigh/max` 需所选模型支持。
- 每次请求一张 PNG；同时兼容接口实际返回的 JPEG/WebP。
- 等待期间会在目标楼层插入一个纯展示的占位：按所选图片比例预留位置，配流光扫过与呼吸点动画，并显示已等待秒数；进入保存阶段后文案切换为“正在把插画保存到酒馆…”。占位不写入聊天数据，图片就位后立即移除，取消、失败或切换聊天同样会清掉。
- 默认最长等待 600 秒，可调整为 30–1800 秒。
- 悬浮按钮可上下拖动；闲置约 2.2 秒后自动吸附到右边缘并变淡（桌面约 32% 不透明度，手机约 50%，因为手机没有鼠标悬停可唤醒），鼠标移入、聚焦或点按即恢复，避免遮挡正文。取消“自动贴边隐藏”可让它一直保持可见。生图进行中即使处于吸附状态也保留稍高的可见度，方便看到进度点。
- 点击外部、关闭按钮或 Esc 可收起面板，收起不会取消生图。点击“取消”会停止等待，但服务端是否停止生成由代理决定。
- “模型回复结束后自动生图”默认关闭，开启后只对之后结束的回复生效。同一层已有插画、正在生图、上一次结果尚未插入、最新楼层是用户消息、或本次生成被用户停止时都会跳过，避免重复消耗额度。
- 生图失败不会自动重试；自动触发跳过后面板状态栏会保留上一次结果。

## 保存与恢复

图片先通过酒馆原生 `/api/images/upload` 保存到酒馆用户图片目录，再记录到聊天消息附件中，最后调用 `saveChat()`。重新打开聊天时由酒馆自己的图片功能渲染。原文不会被图片或 HTML 替换。

生成请求绑定发起时的聊天、消息对象、正文和文本 swipe。等待期间增加新楼层不会改变目标；切换聊天、删除原楼层、编辑正文或切换该楼层的 swipe，会阻止自动插入。生成结果保留在面板内，可以下载，或点击“插入当前所选楼层”明确地转存到当前选择的楼层。

上传失败时点击“重试保存并插入”，只重试保存，不再次生图。聊天保存失败后再次保存也不会重复添加图片。可用“清除预览”放弃内存中的结果，以开始下一次生成；不会删除已经插入的图片或服务器文件。

**尚未保存的结果只保留在当前页面内存中**，刷新或禁用扩展会丢失，请先下载。图片已经上传但聊天保存失败时，服务器上的文件可能仍然存在。

## 密钥与连接

后台转发模式下，浏览器先请求同源酒馆，再由酒馆连接你配置的 CLIProxyAPI；直连模式下，浏览器直接连接 CLIProxyAPI。所选聊天和预设会发给该服务。扩展不包含遥测，也没有其他第三方脚本或运行时依赖。

密钥默认只存在当前页面内存，刷新后需重新填写。勾选“记住密钥”后，会以明文存入酒馆扩展设置，可能随酒馆设置备份或导出；取消勾选会清除持久化副本。后台转发时，Cookie 只用于访问酒馆，当前酒馆原生代理会移除 Cookie 与 CSRF 请求头后再向上游发请求。扩展只传递所需的 CSRF 请求头，不会把酒馆的其他自定义请求头复制给代理。下载返回的图片 URL 时不转发 API Key。后台转发模式下扩展不改动 `Authorization`（该头要留给酒馆自己的登录认证），上游密钥通过 `x-api-key` 传递，CLIProxyAPI 同时接受该头；直连模式仍使用 `Authorization: Bearer`。

常见问题：

| 现象 | 检查事项 |
| --- | --- |
| 提示后台代理尚未启用 | 在实际生效的酒馆 `config.yaml` 中设置 `enableCorsProxy: true` 并重启。 |
| 后台模式无法连接 / 500 / 502 | 检查酒馆服务器到 CLIProxyAPI 的连接、容器网络、内网白名单、前置反代是否允许 `/proxy/` 路由，以及酒馆服务器日志。 |
| 直连模式无法连接 / Failed to fetch | 检查 API 是否运行、端口、CORS 和浏览器混合内容限制；推荐切换后台转发。 |
| 手机连接不上 127.0.0.1 | 先确认连接方式。直连时它指手机；后台时它指酒馆服务器或酒馆容器。 |
| HTTPS 酒馆与 HTTP API | 使用后台模式，浏览器只访问酒馆的 HTTPS；酒馆服务器再访问 HTTP API。 |
| HTTP Basic Auth | 后台转发用 `x-api-key` 传上游密钥，`Authorization` 留给酒馆登录，正常不需要额外处理。若仍收到 Basic 认证挑战，说明这次 `/proxy/` 请求没带上酒馆登录凭据：刷新页面重新登录酒馆，并检查前置反代是否拦掉了 `/proxy/`。 |
| 开了自动生图却没有出图 | 只对开启之后结束的回复生效；该层已有插画、正在生图、上次结果未插入、最新楼层是用户消息或本次生成被停止时都会跳过。可手动点击生成。 |
| 401 / 403 | 使用客户端 API Key，检查密钥及代理权限。 |
| 404 | 检查地址、CLIProxyAPI 版本、图片接口是否被禁用。当前源码配置 `multimedia.disable-image-generation: true` 会禁用图片接口；旧版本配置层级可能不同，以你的版本示例为准。 |
| 模型不支持 / 无图片 | 以你的 `/v1/models` 和该版本 CLIProxyAPI 支持情况为准；能列出模型不等于上游账户一定具备生图权限。 |
| 429 / 超时 | 检查额度、限速和代理日志。扩展不会自动重试；超时后代理仍可能完成生成。 |
| 生成成功但保存失败 | 保留预览，下载图片或点击重试保存；检查酒馆写入权限、反代上传大小限制及磁盘空间。 |

## 接口约定

```http
POST /v1/images/generations
Authorization: Bearer YOUR_CLIENT_KEY
Content-Type: application/json
```

```json
{
  "model": "gpt-image-2.5",
  "prompt": "预设与所选聊天拼接后的完整文本",
  "n": 1,
  "size": "1024x1024",
  "quality": "auto",
  "output_format": "png",
  "stream": false
}
```

解析 `data[0].b64_json`，也兼容 `data[0].url` 的图片 Data URL 或 HTTP/HTTPS 地址。未传 `response_format`，使用 CLIProxyAPI 的默认 Base64 行为。生图本身使用 Images 接口，不使用 `/v1/chat/completions`，无需自行配置 Codex 主线模型或 `image_generation` 工具调用。

选中参考图时改为打到图片编辑端点，`images` 是要一起发送的参考图：

```http
POST /v1/images/edits
Content-Type: application/json
```

```json
{
  "model": "gpt-image-2.5",
  "prompt": "预设 + 聊天情节 + 参考图说明",
  "images": [
    { "image_url": "data:image/png;base64,iVBORw0KGgo…" }
  ],
  "n": 1,
  "size": "1024x1024",
  "quality": "auto",
  "output_format": "png",
  "stream": false
}
```

`images` 必须是对象数组，`image_url` 用 base64 data URL（也接受 http/https，由代理端下载）。同一字段不传即回到纯文本生图。空 `prompt` 会得到 `Invalid request: prompt is required`，缺 `images` 会得到 `Missing required parameter: 'images'`，两张以上时逐张校验（`images[1].image_url`）。CLIProxyAPI 的图片模型白名单为 `gpt-image-1.5`、`gpt-image-2`、`gpt-image-2.5`、`gpt-image-2.5-flare`、`gpt-image-2.5-sunburst`、`grok-imagine-*` 以及自配的 openai-compatibility 图片模型。

形象记忆（可选功能）另走文字接口：

```http
POST /v1/chat/completions
Content-Type: application/json
```

```json
{
  "model": "形象记忆里填写的文字模型",
  "messages": [{ "role": "system", "content": "…" }, { "role": "user", "content": "…" }],
  "stream": false
}
```

只读 `choices[0].message.content`（兼容数组形式与纯 reasoning 返回）。不发送 `max_tokens` / `temperature`，避免不同渠道的参数校验差异；也没传 `response_format`，靠提示词要求模型输出 JSON，解析时容错。两种请求都遵循同一套连接方式（酒馆后台转发或浏览器直连）；后台转发下上游密钥走 `x-api-key`，`Authorization` 留给酒馆登录。
